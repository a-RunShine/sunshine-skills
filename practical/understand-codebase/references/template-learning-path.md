## 1. 5 分钟懂全貌

> 目标：知道这个项目是干嘛的、整体长什么样。
> 不需要写代码，只需要看。

**步骤**：

1. **读 README.md**（如果存在）— 3 分钟
   - 项目介绍、安装、快速开始
   - 跳过"详细 API 参考"等长篇

2. **看 ARCHITECTURE.md 的"1. 项目一句话定位"** — 30 秒
   - 确认 README 没看错

3. **看 ARCHITECTURE.md 的"3. 顶层架构图"** — 1 分钟
   - 理解模块怎么连、有哪些外部依赖

4. **看 ARCHITECTURE.md 的"5. 模块索引表"** — 30 秒
   - 知道有哪几个模块、各自负责什么

**时间合计**：~5 分钟

## 2. 30 分钟上手

> 目标：能跑起来、能在脑子里画出请求的完整路径。
> 需要读代码，但**只读关键文件**。

**步骤**：

1. **跑起来**（5 分钟）— 按 ARCHITECTURE.md 的部署/运行/测试那节走
   - 装依赖、起数据库、跑迁移、启动服务
   - 跑通一个 hello-world 请求（curl /api/v1/ping 之类）

2. **读入口文件**（5 分钟）
   - 主入口：`<path>`（如 `main.py`、`server.ts`、`cmd/<name>/main.go`）
   - 应用装配点：<如 `app/__init__.py`、`src/server.ts`>
   - 路由注册点：<如 `app/routes.py`、`src/router/index.ts`>

3. **读核心模块的"定位 + 关键文件清单"**（15 分钟）
   - 按 [ARCHITECTURE.md 的"5. 模块索引表"](../ARCHITECTURE.md#5-模块索引) 排序，**从最核心的开始**
   - 每个核心模块打开 modules/<name>.md 看：
     - "1. 定位"（5 秒）
     - "2. 关键文件清单"（按文件大小+入口文件排前 3-5 个）
     - "3. 核心类/函数/接口"（快速扫名字，知道有什么）
   - 跳过"内部架构图/数据流/决策"细节

4. **跟着一个真实请求走一遍**（5 分钟）
   - 选 ARCHITECTURE.md "4. 数据流" 里的典型请求（如"用户下单"）
   - 用 grep 或 IDE 跳转，从 Controller 跟到 Service，跟到 DB
   - 看完能讲清楚"这个请求经过哪几个文件"

**时间合计**：~30 分钟

## 3. 深入贡献

> 目标：要改代码、能写出符合项目风格的 PR。
> 需要精读每个模块。

### 3.1 模块精读顺序

> 按"依赖关系"倒序读：先读最底层（被依赖多的），再读上层（依赖别人的）。
> 这样读上层时，底层已经懂了。

**推荐顺序**（按依赖从底到顶）：

1. `<module-1>` — 最底层（最被别人依赖）
   - 看 modules/<module-1>.md 全文
   - **优先读这 2-3 个文件**（按 Agent 标记的"入门先读文件"）：
     - `<关键文件 1>` — 为什么
     - `<关键文件 2>` — 为什么
     - `<关键文件 3>` — 为什么

2. `<module-2>`
   - ...

3. `<module-N>` — 最上层（用户最近）

### 3.2 改代码前的检查清单

> 准备提 PR 前过一遍：

- [ ] 读了项目的 `CONTRIBUTING.md`（如存在）
- [ ] 跑了 lint：`<command>`
- [ ] 跑了测试：`<command>`
- [ ] 新功能有测试覆盖（按 modules/<name>.md 的"测试覆盖"格式）
- [ ] 命名风格跟现有代码一致
- [ ] 公共 API 改了就在 ARCHITECTURE.md / modules/<name>.md 同步更新

### 3.3 找 bug / debug 流程

1. 报错信息搜代码（grep 错误关键词）
2. 看 ARCHITECTURE.md "4. 数据流" — 走一遍涉及的模块
3. 看 modules/<name>.md 的"6. 数据流" — 看本模块内的处理顺序
4. 加 print/log 跑一遍
5. 实在找不到 → 提交 issue 描述清楚"在哪个模块的哪条路径上"

## 4. 可以暂时跳过

> 这些东西**不是看项目的必要内容**，可以先跳过，需要时再看：

### 4.1 目录跳过
- `<node_modules / venv / target / build / dist / vendor / .git>` — 第三方依赖和构建产物
- `<coverage / .nyc_output / htmlcov>` — 测试覆盖率报告
- `<docs/_build / site>` — 文档构建产物
- `<.idea / .vscode / *.swp>` — IDE 配置

> 完整跳过列表（含 `*.lock`、生成代码等文件级跳过）见 `references/depth-boundaries.md` 的 §跳过 段。

### 4.2 文件跳过
- `*.lock`、`package-lock.json`、`yarn.lock`、`Cargo.lock` — 锁定版本，看 manifest 就够
- `*.min.js`、`*.map` — 压缩后的产物
- `*_pb.go`、`*.gen.ts`、`openapi.json`、`schema.prisma`、`*.graphql` — 生成的代码
- 大测试 fixtures（几千行假数据）— 除非在改测试结构
- `CHANGELOG.md`（除非对比版本差异）
- `LICENSE`（除非要分发）

### 4.3 模块跳过（如果项目很大）
- `examples/`、`demos/` — 演示代码
- `scripts/` — 运维脚本（一次性、跟主流程无关）
- `docs/` — 文档源（除非文档本身就是项目的一部分）
- `migrations/` — 数据库迁移（除非在改 schema）

## 5. 时间投入参考

| 目标 | 预估时间 | 完成标志 |
|---|---|---|
| 5 分钟懂全貌 | 5 分钟 | 能用一句话讲清楚项目干嘛 |
| 30 分钟上手 | 30 分钟 | 能跑起来 + 跟完一个请求 |
| 写第一个 PR | 2-3 小时 | 提一个小的 bug fix 或文档改进 |
| 成为模块 owner | 1-2 周 | 精读完一个核心模块的所有代码 |
| 成为项目 owner | 1-3 月 | 精读所有模块 + 跑过所有测试 + 修过几个非平凡的 bug |

> 时间因人而异。如果你熟悉同类技术栈（同类语言/框架）会快很多。
